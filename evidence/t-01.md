La evidencia corresponde al avance de `feature/api-bootstrap`; las demás tareas siguen pendientes.

## Entorno reproducible

- PHP 8.4 en la imagen oficial fijada por digest en `Dockerfile`.
- Composer 2.10.3 fijado por SHA-256 de su distribución oficial.
- Laravel `v13.36.0` y PHPUnit `12.5.39`, fijados en `composer.lock`.
- Solo dependencias de producción en la imagen de ejecución; PHPUnit se instala en el objetivo `test`.
- No se requieren base de datos, credenciales ni archivo `.env` para consultar salud.

## Verificación ejecutada

[Ejecución inicial de GitHub Actions](https://github.com/valerysinai/test-manager-library-3145555-api/actions/runs/38575336538)
completada con resultado **success** en los trabajos `lockfile` y `bootstrap`.
El archivo de dependencias quedó persistido en `b60bc27`.

El trabajo `bootstrap` acreditó:

1. Construcción del objetivo `test` y ejecución satisfactoria de PHPUnit.
2. Construcción de la imagen de ejecución mediante instalación desde `composer.lock`.
3. Arranque de esa imagen sin un contenedor de base de datos.
4. Consulta HTTP desde el runner a `/api/v1/health`, con respuesta exacta `{"status":"ok"}`.
5. Eliminación del contenedor temporal al terminar.

Las pruebas cubren ocho escenarios: salud pública, cinco rutas inexistentes (incluidos los
prefijos incorrectos y `/up`), método no permitido con cabecera Allow y error interno sin
filtrar detalles aun con debug activado. La configuración de prueba apunta a un host de base
inexistente para que una dependencia accidental del endpoint de salud provoque un fallo.

Comandos reproducibles en el README: construir objetivo `test`, construir imagen de ejecución
y arrancar el contenedor con un comando `docker run`.

## Límites

La verificación ejecutable se realizó en GitHub Actions. Las descargas locales de PHP y Composer
se interrumpieron o agotaron el tiempo de conexión; los archivos incompletos no se ejecutaron.
No se modificó la configuración de red de Windows ni de Docker para eludir el problema.

La consulta de salud acredita el proceso HTTP, no conexión a PostgreSQL, autenticación ni
disponibilidad de otros servicios. No acredita T-02, T-16 completo, T-19 ni el despliegue de T-20.
Este servidor sirve para T-01; el despliegue integrado con HTTPS se documentará en `infra`.

El flujo final de CI tiene solo `contents: read`; el paso temporal de escritura del lockfile
fue retirado después de conservar el resultado. Las ejecuciones posteriores comprueban el
lockfile versionado y no actualizan dependencias ni publican commits.
